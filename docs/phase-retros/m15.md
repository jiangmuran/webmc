# M15 — Advanced Redstone (Retrospective)

## Shipped (pure-logic layer)

- **Piston push/pull**: `computePush(piston, facing, lookup)` scans the facing direction until it hits air or an immovable block, chains up to 12 blocks, reports a `{from, to}` move list or `blocked`. `computePull` handles sticky-piston retraction (single block pulled from 2 cells ahead to 1 cell ahead).
- **Repeater**: 1–4 tick delay queue. Each tick shifts input through a `boolean[]` of length `delay`; output = head of queue. Lock flag freezes state (side-input mechanic).
- **Comparator**: `compare` mode (back passes when back ≥ max(sides), else 0) and `subtract` mode (max(0, back − max(sides))). Container sense: empty = 0, any content = 1, full = 15 with a linear fill-fraction formula.
- **Observer**: pulses 1 tick when an observed hash changes; deterministic via `lastObservedHash`.
- **Hopper step**: moves 1 item/tick from first non-empty source slot to first matching-or-empty dest slot, merging where possible, capped by `maxStack(itemId)`. Empties source slot when last item moves.
- **18 new tests** covering all of the above.

## Cut / deferred

- **All integration** — piston block-state + World mutation, repeater/observer/comparator tile-entities wired to the redstone tick scheduler, hopper pickup from world entities. The pure modules are the hard part; hooking them into `RedstoneWorld` is mechanical once the placement + tile-entity layer is in place.
- **Droppers, Crafters, Dispensers** — same tile-entity scaffolding as hopper; they defer into one pass.
- **Command blocks** — out of scope until scripting sandbox (Post-M17).

## Biggest surprise

Pistons are surprisingly simple once expressed as "scan in a direction + emit move list." MC's real implementation has obscure quirks (honey/slime adjacency pulls, block-entity push rules, corner cases with moving observers) that we can add as the tile-entity layer matures — but the 80% that matters (push up to 12, block on immovable, sticky pull one back) is 30 lines. Same pattern for the other components: keep the tick-time state change pure, let the integration layer decide when to call it.

## What the next milestone should know

- **All five components are independently testable and importable** from `@/redstone/{piston,components}`.
- **`PistonLookup` / `ObserverState` / `RepeaterState`** are the API boundaries — integration code should shape its tile-entity state around these, not the other way around.
- **Hopper transfer count is 1/tick** (matches MC); scaled throughput comes from running it at the redstone tick rate (10 Hz).
- **Piston push order matters**: the `moved` array is ordered from head → chain-end, so callers that apply moves in-place must iterate from the back to avoid overwriting cells that haven't shifted yet.
- **No block registry changes this milestone** — piston/sticky_piston/piston_head/repeater/comparator/observer/hopper/dropper/dispenser blocks still need to be added when we tackle integration.
